## 1. 定位与结论

保留 ddd-agent-sheep 的法律业务定位，吸收方案中的人机协作机制。分两条路径推进：先用规范管理本项目研发，再将版本化交付、人工关卡、打回与审计融入案件工作流。暂不扩展为通用数字员工平台，也不要求先引入 Hermes 或虚拟电脑池。

PDF 中 Hermes 命令、配置、产品能力属于原文陈述，本次未对照其官方网站验证，不作为已确认的实施依据。

## 2. 已核对的现状

- 案件领域已有状态流转、证据、期限和人工审核任务；LegalReviewTask 要求人工身份、意见，律师签署还要求律师角色与引用。
- LegalMatterRepository 已定义租户范围和乐观版本边界，本次只找到 InMemoryLegalMatterRepository 实现。LegalMatterStoreConfig 仅在基础设施关闭时创建内存仓储。
- WorkflowEngine 在单次调用中拓扑执行节点，执行结束后汇总 REVIEW_REQUIRED。本次检查的引擎没有持久化等待真人、批准后从检查点恢复的机制；REVIEW/LAWYER_REVIEW 节点类型本身不代表人工批准。
- 已有治理、案件、审计和工作流界面，适合增量贯通。
- 仓库有大量已有已修改和未跟踪文件。它们是接手现场，不应被重置、清理或默认认定为本次产出。

## 3. 从方案中吸收什么

| 原方案机制 | 本项目研发实践 | 法律产品中的对应机制 |
| --- | --- | --- |
| 项目档案是真实来源（第 5.2 节） | 需求、设计、任务、验收、决策入库并相互关联 | 案件事实、证据和报告有明确来源与版本 |
| 先自检后交付（第 4 章） | 每个变更提供执行过的检查与证据 | Agent 交付结构化草稿、自检与证据引用 |
| 关卡放行（第 4 章） | 明确范围、验收标准和最终验收点 | 关键业务动作由服务端核验人工批准 |
| 交接与打回（第 5.5 节） | 交付物、版本、自检、遗留风险齐全 | 打回后失效相关下游结果，保留历史 |
| 风险分级（第 5.5 节） | 数据、权限、跨层改动重点评审 | 按业务动作决定复核深度，对外签署保留律师边界 |
| 收件箱与 WIP（第 5.3–5.4 节） | 聚合阻塞和待验收工作 | 按审核人展示待审案件、版本与等待时长 |
| 转交与冻结（第 7 章） | 接手记录未完成事项及权限归属 | 转交期间冻结未决审核，新负责人重新接收 |
| 控制面与执行面（第 6 章） | 交付与验收规则独立于编码工具 | 审批和审计独立于模型及 Agent 运行时 |

不把每次本地编辑都变成人工审批点。既有授权范围内的可逆研发工作连续推进；业务关卡针对具有明确责任和交付边界的动作。

## 4. 产品最小融合设计

优先贯通一条流程：创建案件 → 上传材料 → 检索与分析草稿 → 提交人工复核 → 批准或打回 → 律师签署 → 保存最终版本和时间线。

建议的概念（先映射既有领域对象，确认缺口后再新增）：

- 交付物版本：tenantId、matterId、artifactId、version、内容摘要、来源证据版本、生成 runId、生成者及时间。
- 审核请求：关卡类型、交付物版本与摘要、指定审核人、状态、乐观版本、自检结果及风险。
- 审核决策：真实审核身份、批准或打回、意见、依据、时间及被批准的版本。
- 运行检查点：运行身份、工作流定义版本、已完成节点、节点输入输出引用、等待关卡、恢复版本及状态。

以上为设计建议，字段名不是既有 API 契约。

必须满足的约束：

1. 批准绑定交付物版本和内容摘要；内容或依赖证据改变后，旧批准不能放行新版本。
2. 机器自检与人工决策分开记录；模型输出、提示词及前端状态不能充当人工批准。
3. 重复批准、恢复和重试保持幂等；并发决策通过数据库版本条件限制。
4. 打回不直接给当前 DAG 加回边；先记录修订及依赖失效，再创建后续运行或从明确检查点恢复，避免重复外部动作。
5. 案件更新、审核决策、审计及恢复意图形成一致事务；异步派发时采用可靠事件机制。
6. 等待审核跨重启保留；不以长期占用线程或 HTTP/SSE 连接实现等待。
7. 转交、租户范围和审核权限由服务端实施，保留旧负责人和原决策历史。

## 5. 本项目研发先行试点

第一个试点需求：案件和复核任务可靠保存，服务重启后能继续查看及处理。

建议验收标准：

- AC-01：创建案件、记录证据和提交复核后重启，状态、版本及历史不丢失。
- AC-02：其他租户不能读取或修改该案件、附件和审核任务。
- AC-03：两个请求使用同一旧版本更新时，仅一个成功，另一个得到明确冲突。
- AC-04：审核决定与案件更新中途失败时，不出现一半成功的状态。
- AC-05：审核意见、审核人和对应交付物版本可追溯；重复提交不产生重复副作用。
- AC-06：离线内存模式与在线持久化模式有明确配置及诊断，在线缺依赖时明确失败。

以上标准不是已通过的测试结果。启动、构建和测试基线需在实施前实际执行并记录。

## 6. 推荐实施顺序

1. 接手基线：核对工作区变更、有效模块、启动方式与现有检查结果，补齐入口文档。
2. 数据闭环：落地案件、复核和审计的持久化，实现事务与并发约束。
3. 版本关卡：先在现有案件复核流程绑定报告与证据版本，验证批准、打回和旧批准失效。
4. 运行闭环：补充工作流检查点、等待与恢复，连接案件审核，避免并行维护两套审批真相。
5. 使用体验：完善待审收件箱、打回原因、时间线和接手记录。
6. 扩展治理：在实际负荷出现后再加入 WIP、代理转交及更多执行运行时。

暂缓：多项目矩阵管理、全岗位数字员工配置、虚拟电脑池、通用看板平台和 Hermes 专用集成。若未来需要，运行时应通过适配接口接入，不拥有业务批准权。
